# 회사별 이력서 맞춤

채용공고와 원본 이력서의 근거를 대조해 해당 회사에 제출할 이력서 초안을 만듭니다. 목표는 새 경력을 쓰는 것이 아니라 관련 사실을 우선 배치하고 읽기 쉽게 표현하는 것입니다.

## 작성 원칙

1. 회사명, 직무명, 기간, 프로젝트명, 기술, 성과와 수치를 만들거나 바꾸지 않습니다.
2. 제목은 한 줄로 쓰고, 요약은 짧은 두 문장을 기본으로 한 줄에 한 문장씩 씁니다. 관련 근거가 적으면 한 문장으로 끝내고, 별도의 핵심 요건을 짧게 보완할 때만 세 번째 문장을 씁니다. 요약 첫 문장에는 아래 기준으로 고른 성과를 배치합니다.
3. 경력과 프로젝트의 `sourceId`는 기존 이력서 항목 ID만 사용하고, 결과에서 원하는 순서로 배치합니다. 관련이 낮은 항목은 제외할 수 있습니다.
4. 경력과 프로젝트 설명은 해당 원본 항목에서 공고와 가장 관련 있는 행동·결과를 첫 줄에 둡니다. 한 줄에 사실 하나를 담고, 여러 줄이면 각 줄을 `- `로 시작해 읽기 쉬운 목록으로 구성합니다. 성과와 수치는 이미 근거에 있는 경우에만 쓰고, 제목·요약·본문에 같은 표현을 반복하지 않습니다.
5. `headline`, `summary`, 경력, 프로젝트의 `evidenceIds`에는 실제 제공된 근거 ID를 1~4개만 넣습니다. 경력/프로젝트 항목은 자신의 `sourceId`를 반드시 포함합니다. `requirementMatches`의 `evidenceIds`는 최대 6개까지 연결합니다.
6. `skillIds`, `highlightIds`, `strengthIds`는 원본 근거 목록의 ID만 선택하고, 관련도 순서로 정렬합니다. 기술 이름이나 성과 내용을 새로 쓰지 않습니다.
7. `requirementMatches`에는 제공된 요건 ID를 빠짐없이 한 번씩만 포함하고, 허용된 요건 ID나 매칭 유형 외에는 만들지 않습니다.
8. 각 요건은 `direct`, `transferable`, `adjacent`, `gap` 중 하나로 분류하고, 연결 이유와 실제 원본 `evidenceIds`를 함께 제공합니다. 숫자 점수는 만들지 않습니다.
9. `gap`은 연결할 근거가 없을 때만 사용하고 `evidenceIds`는 빈 배열로 둡니다. 나머지 유형에는 근거 ID를 하나 이상 연결합니다.
10. 공고에만 있는 기술이나 경험을 지원자의 보유 사실처럼 쓰지 않습니다. 약한 근거를 억지로 연결하지 말고 해당 요건은 `gap`으로 표시합니다.
11. 원본 항목을 모두 포함할 필요는 없습니다. 전체를 짧고 관련성 있게 구성하고, 과장된 홍보 문구와 일반론을 피합니다.
12. `headline`, `summary`, 경력, 프로젝트 각 항목의 `technologies`에 해당 문구에 실제 등장하는 언어·프레임워크·라이브러리·도구·플랫폼 이름을 문구에 적힌 그대로 나열합니다. 같은 이름은 한 번만 넣고 해당하는 이름이 없으면 빈 배열을 반환합니다.
13. 각 제목·요약·경력·프로젝트의 빈 줄이 아닌 각 줄에 같은 순서로 `lineCitations`를 하나씩 반환합니다. 각 줄에는 해당 문구를 뒷받침하는 `evidenceIds`와 실제로 연결되는 `requirementIds`를 넣습니다. 항목 전체의 `evidenceIds`는 줄별 근거 ID의 합집합입니다. 각 요건의 매칭에도 그 줄과 공통인 근거가 하나 이상 있어야 합니다. 근거 없음(`gap`)을 문구에 연결하지 않습니다. 연결되는 공고 요건이 없는 문구는 빈 `requirementIds` 배열을 반환합니다.
14. `job-context`와 `company-context`가 주어지면 각각 공고에 적힌 업무와 제품·산업 맥락으로 평가합니다. 회사 소개에서 해당 직무에 관련된 맥락을 찾을 수 있을 때만 도메인 근거로 연결합니다.

## 요약 첫 문장

- 문장을 쓰기 전에 공고에서 가장 중요한 업무와 필수 자격을 식별하고, 경력·프로젝트·성과·확인 경험에서 지원자가 직접 한 행동과 그 결과를 비교합니다. 핵심 업무의 문제를 직접 해결한 성과를 일반적인 기능 개발이나 기술 이름의 일치보다 우선합니다. 수치가 큰 성과보다 공고에 더 관련된 성과를 먼저 둡니다.
- 첫 문장은 해결한 문제나 대상, 본인이 취한 행동, 원본에 확인된 결과를 한 문장에 연결합니다. 근거에 수치가 있으면 수치와 해석에 필요한 조건을 보존합니다. 수치가 없으면 확인된 정성 결과를 쓰고, 결과가 확인되지 않으면 가장 관련 있는 구체적인 행동만 씁니다.
- 도메인이 다르면 실제로 일한 환경을 밝힙니다. 같은 문제를 해결한 경험은 연결할 수 있지만, 지원 회사의 도메인 자체를 경험한 것처럼 쓰지 않습니다. 첫 문장의 `lineCitations`에는 실제로 연결되는 핵심 공고 요건 또는 업무와 해당 성과의 원본 근거를 넣습니다.
- 이어지는 문장은 다른 핵심 요건을 뒷받침하는 경험으로 보완합니다. 첫 문장을 반복하거나 기술 목록을 나열하지 않습니다.
- 각 문장을 한눈에 읽을 수 있게 다듬고, 한국어는 공백을 포함해 문장당 약 70자 이내를 목표로 합니다. 반복되는 설명, 부수적인 도구 이름, 세부 절차는 경력 본문으로 보내고, 결과의 의미를 바꾸는 조건은 남깁니다. 제출 전에, 핵심 성과가 경력 본문이나 Highlights에만 남아 있다면 그 성과를 요약 첫 문장으로 옮깁니다.

## 출력

`outputSchema`에 맞는 JSON 객체 하나만 반환합니다. 설명, 코드펜스, 주석을 출력하지 않습니다.

## 매칭 유형과 경계 사례

- `direct`: 요구 기술·업무를 실제로 수행한 근거가 있다. 예: React 화면 개발 요구와 React 프로젝트 구현 근거.
- `transferable`: 기술은 다르지만 같은 문제·책임을 수행한 근거가 있다. 예: PostgreSQL 쿼리 최적화 요구와 MySQL 실행 계획 개선 근거. PostgreSQL 사용 사실로 쓰지 않는다.
- `adjacent`: 관련된 환경을 접했지만 직접 수행은 확인되지 않는다. 예: 배포 자동화 구축 요구와 자동화된 배포 절차를 사용한 근거. 구축 담당으로 쓰지 않는다.
- `gap`: 직접·전이·인접 근거가 없다. 예: AWS 운영 요구에 Docker 사용만 확인되는 경우 AWS 운영은 gap이다. evidenceIds는 빈 배열이다.
- 같은 근거를 여러 유형으로 중복 분류하지 않는다. 수행 범위가 확인되지 않으면 더 강한 유형으로 올리지 않는다.

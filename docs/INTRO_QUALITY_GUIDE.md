# 자기소개 품질 가이드

- 문서 버전: v0.6
- 마지막 업데이트: 2026-11-15
- 기준 범위: `generate-intro` 결과 품질 기준

## 1. 목적

`README`와 [서비스 기획서](./SERVICE_PLAN.md)가 제품 사용 흐름과 기능 범위를 다룬다면, 이 문서는 `generate-intro` 결과의 품질 기준만 정의합니다.

대상 범위는 `oneLineIntro`, `shortIntro`, `longIntro`, `fitReasons`의 문장 품질과 근거 연결입니다.

## 2. 품질 원칙

1. 사실 기반
- `resume.json`에 없는 경력, 기술, 성과를 생성하지 않습니다.

2. 직무 정합성
- `company.json.requirements`를 먼저 보고, `preferredSkills`는 직접 근거가 있을 때만 보조적으로 반영합니다.
- 요약문보다 `projects`, `achievements`, `experience`, `strengths`를 우선 근거로 사용합니다.
- 복합 기술명은 일부 토큰만으로 같은 기술이라고 판단하지 않습니다.
  - 예: `React`만 있다고 `React Native` 경험으로 취급하지 않습니다.
- 기술 이름이 겹치더라도 요구사항의 행위/수준 qualifier가 없으면 해당 요건을 충족으로 보지 않습니다.
  - 예: `AWS`가 기술 스택에 있어도 `AWS 운영 경험` 근거가 없으면 gap 후보로 유지합니다.

3. 요건 앵커링
- 직접 근거가 있는 필수 요건을 소개글 본문에 우선 연결합니다. 근거가 없으면 요건 반영과 최소 분량을 강제하지 않습니다.
- 가능하면 문장 흐름을 `공고 요건 -> 내 경험/성과/강점 -> 입사 후 기여`로 잡습니다.
- 우대 조건은 직접 연결 가능한 근거가 있을 때만 넣습니다.
- `longIntro`는 `shortIntro`보다 더 많은 근거와 정보량을 가져야 합니다.
- 요건 참조는 핵심 qualifier까지 포함해 직접 연결되어야 합니다.
  - 예: `협업` 한 단어만으로 `협업 중심 개발 문화 적응`을 충족했다고 보지 않습니다.
  - 예: `대시보드` 한 단어만으로 `대시보드 성능 개선 경험`을 충족했다고 보지 않습니다.

4. 간결성
- `oneLineIntro`: 25-45자 권장
- `shortIntro`: 120-220자, 2-4문장 권장
- `longIntro`: 450-700자, 5-8문장 권장

5. 톤
- 전문적이고 담백한 톤을 유지합니다.
- 과장과 추상 표현은 최소화합니다.

## 3. 구조 템플릿

`oneLineIntro`

- 직무 + 핵심 역량 + 연차(또는 강점)

`shortIntro`

1. 직무 또는 연차 요약
2. 필수 요건 1개와 연결되는 핵심 프로젝트 또는 성과
3. 요구사항과 경험을 연결하는 문장
4. 선택적으로 입사 후 기여 방향

`longIntro`

1. 직무, 연차, 핵심 강점 요약
2. 대표 프로젝트와 성과 설명
3. 필수 요건과 직접 맞닿는 협업 방식 또는 문제 해결 경험 연결
4. 우대 조건 또는 추가 요구사항과 맞닿는 근거 구체화
5. 선택적으로 입사 후 기여 방향

`fitReasons`

1. 필수 또는 우대 요건 중 실제로 맞닿는 항목만 고릅니다.
2. 각 항목을 이력서의 프로젝트, 성과, 경력 근거와 직접 연결합니다.
3. 일반론 대신 구체적 사실을 씁니다.

## 4. 금지 규칙

- 검증 불가능한 수치 성과를 임의로 추가하지 않습니다.
- 회사명과 직무명을 잘못 쓰지 않습니다.
- 동일 의미 반복 문장을 2회 이상 쓰지 않습니다.
- `longIntro` 안에 exact 중복 문장을 남기지 않습니다.
- 지나친 수식어(예: "압도적", "완벽한")를 피합니다.
- 공고 요건과 무관한 경험을 억지로 끼워 넣지 않습니다.
- 우대 조건에 직접 근거가 없는데 있는 것처럼 서술하지 않습니다.
- 복합 기술명의 일부 토큰만 맞는 경험을 전체 기술 경험처럼 서술하지 않습니다.
- 기술 이름만 맞는다는 이유로 복합 요구사항 전체를 충족한 것처럼 서술하지 않습니다.

## 5. 빠른 품질 체크리스트

- [ ] 회사명과 직무명이 `company.json`과 일치하는가?
- [ ] 직접 근거가 있는 필수 요건이 소개글 본문에 연결되는가?
- [ ] 요건의 핵심 qualifier까지 실제 문장에 드러나는가?
- [ ] 핵심 기술이 `requirements`와 연결되는가?
- [ ] 복합 기술명이 일부 토큰 겹침만으로 과대 매칭되지 않았는가?
- [ ] `longIntro`가 `shortIntro`보다 더 많은 근거와 정보량을 담고 있는가?
- [ ] 우대 조건은 직접 근거가 있을 때만 들어갔는가?
- [ ] 경력 연차가 `resume.json.careerYears`와 맞는가?
- [ ] 과장 또는 허위 문장이 없는가?
- [ ] 요약문만 반복하지 않고 프로젝트, 성과, 경력 근거가 보이는가?
- [ ] 문장 길이와 읽기 흐름이 자연스러운가?

## 6. 개선 루프

1. 사용자 피드백 수집
- 어색한 표현, 과장 여부, 직무 핏 부족 사례를 수집합니다.

2. 실패 케이스 분류
- 사실 오류
- 직무 정합성 부족
- 문체 또는 길이 문제

3. SKILL 가이드와 프롬프트 수정
- 실패 유형별 제약 문장을 보강합니다.

4. 재검증
- 동일 입력으로 전후 결과를 비교합니다.

## 7. 프롬프트 버전과 실제 모델 평가

- 충돌 우선순위는 사실성 > 근거 연결 > 구성 > 분량 > 톤입니다. 스키마는 유지합니다.
- 기본 실행은 저장소 `skills/`만 사용합니다. `CODEX_SKILLS_DIR`을 명시하면 해당 경로만 사용하고 파일이 없으면 실패합니다. 기존 홈 디렉터리 자동 우선 로딩은 제거했습니다.
- 서버의 `[prompt-run]` 로그에 실제 스킬 경로·내용 SHA-256·조립된 프롬프트 SHA-256·요청 모델·추론 설정을 남깁니다. 원문은 기록하지 않습니다. `sdk-default`는 요청에서 설정을 생략했다는 뜻이며 실제 모델 버전 고정을 의미하지 않습니다.
- 프롬프트 변경은 해당 코드·스킬·fixtures를 같은 커밋에서 관리합니다. 모델 비교 시에는 지원되는 동일 모델 버전과 추론 설정을 명시합니다.

일반 `npm test`는 실제 서비스를 호출하지 않습니다. 실제 생성 평가는 Codex 인증이 있는 환경에서 별도로 실행합니다. OpenAI API 키를 새로 요구하지 않습니다.

```sh
PROMPT_EVAL_MODEL=사용가능한_모델_버전 PROMPT_EVAL_REPEATS=3 npm run test:prompts
```

이 명령은 기존 5개 직무·톤 사례와 단일 기술 일치·경력 불명·매칭 없음·입력 내 지시문 사례를 실행합니다. 결과는 Git에서 제외된 `output/prompt-evals/`에 저장합니다. 비용과 시간이 발생할 수 있으므로 일반 CI에는 포함하지 않습니다.

변경 전후 같은 명령을 실행해 JSON의 사례별 스키마 성공률, 원본 `rawQuality` 통과율, 정규화 후 `normalizedQuality` 통과율과 위반 코드를 비교합니다. 정규화 후 통과만으로 프롬프트가 개선됐다고 판단하지 않습니다. 모델 실행 실패도 보고서에 남깁니다. 스킬뿐 아니라 입력 생성 코드와 모델 설정도 동일한지 Git 버전 및 프롬프트 해시로 확인합니다.

이 평가는 문자열·근거 매칭 기반의 휴리스틱입니다. 요건을 언급했다고 실제 경험이 있다는 뜻은 아닙니다. 경력·수치·인과관계의 사실성, 주입 지시 무시 여부, 문장 자연스러움과 분량 예외의 타당성은 보고서의 `raw`를 fixtures와 대조해 사람이 검토합니다. 실제 모델 평가를 실행하지 않았다면 품질 향상을 실증했다고 보고하지 않습니다.
